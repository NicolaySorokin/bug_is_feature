# Система контроля взаимодействия ИТ Школы Ростелекома с вузами

Веб-система для ИТ Школы Ростелекома: вузы и ответственные, договоры
с ИТ-программами, продуктами и лицензиями, путь взаимодействия с вузом
по шагам рабочего процесса, отчёты и статистика обучения, обмен с LMS
и сайтом, загрузка каталогов из Excel.

- Боевой стенд — https://edu-crm.nikitarodionov.ru (API — `/docs`)
- Соответствие ТЗ по пунктам — [docs/requirements.md](docs/requirements.md)
- Библиотеки и версии — [docs/libraries.md](docs/libraries.md)
- Архитектура в Archi — [docs/architecture](docs/architecture/README.md)
- Руководства пользователя, администратора и системного администратора
  встроены в систему: раздел «Руководства»

## Запуск

Нужны только Docker и make.

```bash
make build   # собрать образы и подготовить проект
make up      # запустить: контейнеры, миграции, демоданные
```

Дальше:

- Система — http://localhost:3000. В разработке пароля нет: на экране входа
  выберите учётную запись (`petrov` — менеджер, `fedorov` — руководитель,
  `admin` — администратор)
- Swagger UI — http://localhost:8000/docs
- OpenAPI — http://localhost:8000/api/v1/openapi.json
- Проверка живости — http://localhost:8000/api/v1/health

`make down` останавливает стенд, `make reset` — сносит вместе с данными
и собирает заново. Клиентскую часть с горячей перезагрузкой запускает
`npm run dev` — см. [frontend/README.md](frontend/README.md).

## Среды

Состав стенда описан в корневом `docker-compose.yml` и одинаков везде;
отличия сред лежат в `cicd/<среда>/docker-compose.yml`:

| Среда | Отличия |
| --- | --- |
| `dev` | система на порту 3000, код API монтируется, сервер перезапускается сам, порты открыты, авторизация — заглушка |
| `preprod` | как на бою, но по HTTP; наружу смотрит Nginx; авторизация через Keycloak |
| `prod` | HTTPS, несколько рабочих процессов, ограничения памяти, перезапуск при падении |

Секреты задаются файлом `.env` рядом с конфигурацией среды
(`cicd/prod/.env`), в репозиторий он не попадает — есть только `.env.example`.

Боевой стенд https://edu-crm.nikitarodionov.ru обновляется сам после
зелёного CI на `main`: как устроен деплой, где смотреть логи и как
откатиться — в [cicd/README.md](cicd/README.md#боевой-стенд-автоматический-деплой).

## Зависимости

`backend/requirements.txt` задаёт диапазоны версий, `backend/requirements.lock` —
снимок того, что реально стоит в собранном образе, вместе с зависимостями
зависимостей. Dockerfile ставит из lock, если файл есть, поэтому сборка
повторяется один в один. После правки `requirements.txt`:

```bash
make build && make lock
```

Клиентская часть ставится строго по `frontend/package-lock.json` (`npm ci`).

## Интерфейс

Одностраничное приложение: страница не перезагружается, после действия
обновляются только затронутые данные. Разделы бокового меню:

| Раздел | Что там | Кому |
| --- | --- | --- |
| Главная | сводка по роли, договоры, требующие действия, следующие шаги | всем |
| Договоры | реестр с фильтрами; карточка: сведения, схема процесса с переходами, комментарии и файлы, состав программ и продуктов с лицензиями, ответственные от вуза, история | всем |
| Вузы | список и карточка вуза, ответственные от вуза, назначение менеджера | всем, правка — руководителю |
| Отчёты и статистика | отчёт по взаимодействию с вузами, статистика обучения, заявки; выгрузки XLSX, XLS, PDF, JSON, диаграммы PNG и PDF | всем |
| LMS и сайт | источники, синхронизация, загрузка ответа файлом JSON, журнал обменов | руководителю и администратору |
| Пользователи и права, Справочники, Загрузка из Excel, Рабочие процессы, Журнал изменений, Настройки | администрирование | администратору |
| Руководства | пользователю, администратору, системному администратору | всем |

Работает на телефоне: меню выезжает, таблицы становятся карточками.
Устройство клиентской части — [frontend/README.md](frontend/README.md).

## Документация API

Схема описывается не отдельным файлом, а выводится из моделей и аннотаций,
поэтому не расходится с кодом:

- Swagger UI — http://localhost:8000/docs
- ReDoc — http://localhost:8000/redoc
- схема — http://localhost:8000/api/v1/openapi.json

Для клиентской части схема выгружается в файл: `make openapi` кладёт её
в [docs/openapi.json](docs/openapi.json), по нему генерируются типы
клиента (`npm run api:types`). CI сверяет и файл с кодом, и типы
с файлом — изменение API без обновления схемы и типов не пройдёт.

Описания отказов общие для всех методов и собраны в одном месте
([app/api/openapi.py](backend/app/api/openapi.py)): в Swagger у каждого
метода видно и формат тела ошибки, и список кодов.

## Авторизация и права

`AUTH_BACKEND=dev` (по умолчанию) включает заглушку: токен не проверяется,
пользователь берётся из заголовков запроса. Интерфейс в этом режиме
показывает список учётных записей вместо формы входа.

```bash
curl http://localhost:8000/api/v1/me \
  -H "X-Dev-User: petrov" \
  -H "X-Dev-Roles: manager"
```

Роли: `manager` (Пользователь / КАМ), `head` (Руководитель), `admin`
(Администратор). Без заголовков подставляется пользователь из `DEV_USER_*`
со всеми ролями.

Что может каждая роль:

- **менеджер** видит договоры, где он ответственный или закреплён за вузом,
  и вузы, которые ему открыл администратор; ведёт процесс, пишет
  комментарии, прикладывает файлы, ведёт лицензии;
- **руководитель** видит все договоры, назначает, меняет и снимает
  ответственных за вузы и договоры, правит вузы, переименовывает этапы,
  пропускает любые этапы, запускает обмен с LMS и сайтом, видит заявки
  с персональными данными;
- **администратор** — всё то же, плюс пользователи и права (роли пишутся
  в Keycloak, отключение учётной записи, доступ к данным «свои вузы» или
  «все», дополнительно открытые вузы), справочники, загрузка из Excel,
  шаблоны процессов, журнал изменений, настройки, удаление записей.

Права проверяются сервером в каждом запросе, интерфейс лишь прячет
недоступные кнопки. Запись пользователя находится в каждом запросе,
поэтому отключённая учётная запись не выполнит ни одного действия,
а любое изменение попадает в журнал от имени автора.

Демоданные заводятся под ту схему входа, что настроена при загрузке:
под dev-заглушкой это `petrov` (14 договоров, 6 тревог на главной)
или `orlova` и `fedorov` с ролью `head` (все договоры). Кто есть в системе
и что показывать, описано в [testdata/README.md](testdata/README.md).

### Keycloak

```bash
make keycloak                   # поднимет Keycloak, перенесёт реалм, напечатает пароли
AUTH_BACKEND=keycloak make up    # или задайте переменную в .env
```

Реалм `edu-crm` ([deploy/keycloak/realm-export.json](deploy/keycloak/realm-export.json))
содержит роли, клиент `edu-crm-api` (аудитория токена), публичный клиент
`edu-crm-web` для интерфейса и 23 пользователя: 20 менеджеров
(`petrov`, `ivanova`, …), руководители `orlova` и `fedorov`, администратор
`admin`. Интерфейс входит только через страницу Keycloak (Authorization
Code + PKCE): выдача токена по паролю в обход неё у `edu-crm-web`
выключена. Включены политика паролей (от 12 знаков, строчные, заглавные
и цифры, не совпадает с логином), защита от подбора, журнал входов
и страница входа в стиле Ростелекома (тема
[deploy/keycloak/image/themes/edu-crm](deploy/keycloak/image/themes/edu-crm)).

**Паролей в репозитории нет.** Их задаёт переменная
`KEYCLOAK_USER_PASSWORDS` среды — пары `логин:пароль` через запятую;
на боевом стенде это одноимённый секрет репозитория. Новые пароли для
всех пользователей реалма генерирует тот же скрипт:

```bash
cd backend && KEYCLOAK_REALM_FILE=../deploy/keycloak/realm-export.json \
  python -m scripts.keycloak_setup --generate-passwords
```

В разработке (`make keycloak`) недостающие пароли генерируются
и печатаются в консоль.

Keycloak собран под PostgreSQL и хранит данные в своей базе `keycloak`
того же сервера PostgreSQL, поэтому пересоздание контейнера ничего не
сбрасывает. Выгрузка реалма импортируется только при самом первом запуске,
дальше её переносит в работающий Keycloak разовая задача `keycloak-setup`
([scripts/keycloak_setup.py](backend/scripts/keycloak_setup.py)) — её
запускают `make up` в preprod и prod и деплой:

- настройки реалма и клиентов приводятся к выгрузке, адреса возврата
  после входа — адреса интерфейса этой среды из `CORS_ORIGINS`;
- недостающие роли, клиенты и пользователи заводятся, существующие
  пользователи не трогаются — их роли меняют из интерфейса CRM;
- пароли ставятся тем, у кого пароля ещё нет; сменить всем на значения
  из секрета — `make keycloak-setup ARGS=--reset-passwords`.

Внешний и внутренний адреса Keycloak разные: издатель токена проверяется
по `KEYCLOAK_BASE_URL` (так Keycloak видит браузер), а ключи реалма API
забирает по `KEYCLOAK_INTERNAL_URL` (имя контейнера). Снаружи, через Nginx,
открыт только реалм `edu-crm`: реалм `master` и консоль администратора
Keycloak из интернета недоступны.

У пользователей реалма фиксированные `id`, они выводятся из логина
([scripts/demo/people.py](backend/scripts/demo/people.py)). Поэтому сид,
запущенный с `AUTH_BACKEND=keycloak`, заранее знает, кому отдать договоры:
`petrov`, войдя через Keycloak, видит свои договоры. Под dev-заглушкой
те же пользователи получают идентификатор `dev:<логин>`. Если сменили
`AUTH_BACKEND` после загрузки, выполните `make reset`. Новый пользователь
Keycloak заводится в базе при первом обращении, и договоры ему назначает
руководитель. ФИО из токена берётся только при первом входе: дальше им
распоряжается CRM, потому что в отчётах нужно полное ФИО.

Обе схемы реализуют один интерфейс `AuthBackend`
([app/core/security.py](backend/app/core/security.py)), остальной код
про разницу не знает.

## Ошибки

Любой отказ возвращает одно и то же тело — требование о кодах ошибок
из нефункциональных требований ТЗ:

```json
{ "code": "workflow_rule_violated", "message": "Такой переход не предусмотрен...", "details": null }
```

`code` машиночитаем и не меняется вместе с текстом сообщения. Полный
список — в `GET /api/v1/meta/enums`. Интерфейс показывает понятный текст
и код, а раздел руководства «Если что-то пошло не так» объясняет, что
делать с каждым.

## Рабочий процесс

Шаблон версионируется: этапы и переходы принадлежат версии
(`workflow_versions`), экземпляр процесса жёстко привязан к своей версии.
Поэтому правка шаблона не меняет уже запущенные процессы: менять можно
только черновик, а после публикации — только создать новую версию.
Исключения — координаты узлов схемы и названия этапов (руководитель
корректирует их в опубликованной версии, требование 2 ТЗ).

Состояния этапов (не начат, активен, завершён, пропущен, заблокирован)
нигде не хранятся — они вычисляются из истории переходов
(`workflow_events`) и текущего этапа экземпляра.

В демоданных два шаблона ([scripts/demo/processes.py](backend/scripts/demo/processes.py)).

Основной шаблон — это 14 шагов базового workflow из ТЗ, от поиска контактов
до контроля исполнения. «Корректировка документов» в нём необязательна.
Шаблон существует в двух версиях: во второй необязательным стало и
повышение квалификации. Договоры, начатые до выхода второй версии,
идут по первой.

```
Поиск контактов -> Уточнение программ -> Встреча -> Обмен документами -> [Корректировка] -> Подписание
-> Передача материалов и лицензий -> Сопровождение внедрения -> Обучение преподавателей
-> Актуализация программы -> Ведение занятий -> Актуализация документации
-> Повышение квалификации -> Контроль исполнения
```

Короткий шаблон «Дополнительное соглашение» — маршрут из концепции:

```
Контакт -> Встреча -> Документы -> Согласование -> Подписание
                                        `-> Доработка -> Согласование
```

| Метод | Назначение |
| --- | --- |
| `GET /api/v1/contracts/{id}/workflow` | схема, состояния этапов, история, доступные переходы |
| `POST /api/v1/contracts/{id}/workflow` | запустить процесс по шаблону |
| `POST /api/v1/workflow/instances/{id}/transition` | перейти на разрешённый этап |
| `POST /api/v1/workflow/instances/{id}/skip` | пропустить необязательный этап с причиной |
| `POST /api/v1/workflow/instances/{id}/block` | заблокировать процесс |
| `PATCH /api/v1/workflow/stages/{id}` | переименовать этап (руководитель) |
| `PUT /api/v1/workflow/versions/{id}/graph` | сохранить схему черновика |
| `POST /api/v1/workflow/versions/{id}/publish` | опубликовать версию |

## Отчёты и диаграммы

Фильтры передаются телом запроса, одна выборка даёт и таблицу, и диаграммы —
поэтому цифры в них всегда совпадают.

```bash
curl -X POST "http://localhost:8000/api/v1/reports/export?format=xlsx" \
  -H "Content-Type: application/json" \
  -d '{"filters": {"date_from": "2026-01-01"}, "columns": ["university", "program", "stage", "manager"]}' \
  -o report.xlsx
```

- форматы отчёта: `xlsx`, `xls`, `pdf`, `json`;
- форматы диаграммы (`POST /reports/chart`, `POST /statistics/chart`): `png`, `pdf`;
- доступные колонки: `GET /reports/columns`;
- период считается по дате подписания, дате заведения или по движениям
  процесса — параметр `period_basis`.

Строка отчёта — это договор в разрезе одной ИТ-программы, ИТ-продукты
договора собраны в одну ячейку. Если размножить строки ещё и по продуктам,
договор посчитается несколько раз и диаграммы соврут.

Выгрузки собираются в очереди с пониженным приоритетом
([services/export/runner.py](backend/app/services/export/runner.py)):
каждый процесс API строит не больше `EXPORT_CONCURRENCY` файлов
одновременно (по умолчанию 1), остальные ждут. Так десять одновременных
отчётов не отнимают процессор у интерфейса.

## Интеграции

Контрактов API LMS и сайта пока нет, поэтому между внешней системой
и остальным кодом стоит адаптер. Формат записей взят из данных
кейсодержателя: заявки сайта («Номер заявки», «Курс», ФИО, телефон,
почта, «Номер потока») и анкеты LMS. Пока адрес источника не задан,
адаптер отвечает тестовыми данными из
[fixtures](backend/app/services/integrations/fixtures); выгрузку можно
загрузить и файлом JSON (`POST /integrations/sources/{code}/upload`).
При появлении реального контракта меняется только разбор ответа внутри
адаптера.

```bash
curl -X POST http://localhost:8000/api/v1/integrations/sync
```

Синхронизация обновляет справочники и вузы, по новым заявкам вузов
заводит договор и запускает рабочий процесс, заявки на обучение добавляет
в процессы договоров. Повторный запуск дублей не создаёт: для каждой
внешней записи хранится связь в `external_links`. Из анкет LMS сохраняются
только ФИО, контакты, пол, образование и регион — паспорт, СНИЛС, адрес
и сведения о дипломе отбрасываются (152-ФЗ), что записывается в журнал
обмена.

Адреса реальных систем задаются переменными `LMS_BASE_URL`, `LMS_TOKEN`,
`SITE_BASE_URL`, `SITE_TOKEN`.

## Импорт каталогов

Порядок работы: файл → предпросмотр с сопоставлением колонок → проверка
→ импорт → итог «создано / обновлено / отклонено». Проверка выполняет
загрузку целиком и откатывает её, поэтому заранее показывает точный итог
и все ошибки, ничего не записывая.

```bash
# образец с нужными заголовками
curl -o template.xlsx "http://localhost:8000/api/v1/imports/template?type=catalog"
```

Типы загрузок: сводный каталог (все поля из требования 1 ТЗ), вузы,
ответственные от вузов, ИТ-программы, ИТ-продукты, вендоры с их
контактами, анкеты обучающихся из LMS. Колонки узнаются по заголовкам
и синонимам, сопоставление можно поправить вручную. Строка с ошибкой
отклоняется целиком: каждая строка пишется в своей точке сохранения.

## Контроль проблемных процессов

`GET /api/v1/dashboard/alerts` собирает договоры, по которым требуется
действие: этап долго не менялся (норма берётся из `sla_days` этапа),
процесс заблокирован или не запущен, заканчивается срок договора или
лицензии, не назначен ответственный, не загружены документы, не начато
внедрение, не прошла синхронизация. Для каждого случая видны причина,
ответственный и сколько времени ситуация не меняется.

## Кэш

Сводки на главной, тревоги и выборки отчётов кэшируются на сервере
и сбрасываются при любом изменении данных (счётчик версии данных в базе,
общий для всех процессов API). Клиент кэширует ответы и обновляет их
в фоне, а фильтры, выбранные колонки и черновики комментариев помнит
между сеансами — требование 13 ТЗ.

## Условия и ограничения

- **Формат xls.** Отчёт `format=xls` — настоящий двоичный Excel 97 (xlwt).
  У формата предел 65 535 строк, поэтому в XLS попадает не больше
  65 000 строк, полный набор — в XLSX. Загрузка файлов `.xls` тоже
  поддерживается — их читает xlrd.
- **PDF.** Кириллица требует шрифта DejaVu; в образе он ставится пакетом
  `fonts-dejavu-core`. Если шрифт не найден, отчёт формируется стандартным
  Helvetica, о чём пишется предупреждение в лог. В PDF попадает не больше
  1000 строк, полный набор данных — в XLSX.
- **Файлы.** Допустимые форматы вложений — png, jpeg, pdf, zip, gzip, rar,
  doc, docx, xls, xlsx; ограничение размера — `MAX_UPLOAD_MB` (25 МБ).
  Содержимое лежит на диске, в базе — только путь и сведения о файле.
- **Процесс.** У договора один активный процесс; у программ и продуктов
  внутри договора — простой статус внедрения.
- **Статусы** договоров, лицензий и программ (`app/enums.py`) —
  предположение до согласования с заказчиком.
- **Интеграции** работают на тестовых ответах и загрузке файлом, пока
  организаторы не передали контракты API.

## Запуск без Docker

cd backend

cp .env.example .env                                 # укажите свой PostgreSQL

## Проверки при изменениях

[GitHub Actions](.github/workflows/ci.yml) запускается на каждый push
и pull request:

- **Тесты и стиль** — Ruff (проверка и форматирование), тесты
  с PostgreSQL, миграции, сверка моделей с миграциями, загрузка
  демоданных, актуальность `docs/openapi.json`;
- **Клиентская часть** — актуальность типов API, TypeScript, ESLint,
  Prettier, тесты, сборка;
- **Сборка образов** — образы API, Nginx с клиентской частью и Keycloak,
  проверка конфигураций сред и скриптов сервера (shellcheck).

Результат виден галочкой у коммита и блоком Checks в pull request,
итог прогона тестов — на странице проверки.

Чтобы ветку нельзя было слить с падающими проверками, в настройках
репозитория включается Settings → Branches → Add rule для `main`:
«Require status checks to pass before merging» и отметить проверки
«Тесты и стиль», «Клиентская часть» и «Сборка образов».
