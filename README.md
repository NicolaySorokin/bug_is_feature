# Система контроля взаимодействия ИТ Школы Ростелекома с вузами

Веб-система для сотрудников ИТ Школы Ростелекома, которые работают с вузами.
Центральный объект системы: **взаимодействие с вузом**. У взаимодействия есть
вуз, ответственный менеджер, рабочий процесс по этапам, ИТ-программы и продукты,
контакты, файлы и история. Договор с лицензиями появляется по ходу работы
и не обязателен. Кроме того, в системе есть отчёты, статистика обучения,
обмен с LMS и сайтом и загрузка каталогов из Excel.

- Стенд: https://edu-crm.nikitarodionov.ru, Swagger UI: `/docs`
- Соответствие ТЗ по пунктам: [docs/requirements.md](docs/requirements.md)
- Библиотеки и версии: [docs/libraries.md](docs/libraries.md)
- Решения по бизнес-модели: [docs/business-model-decisions.md](docs/business-model-decisions.md)
- Модель архитектуры в Archi: [docs/architecture/edu-crm.archimate](docs/architecture/edu-crm.archimate)
- Руководства менеджера, руководителя, администратора и системного
  администратора встроены в систему, раздел «Руководства»

## Быстрый старт

Нужны Docker и make.

```bash
make build   # собрать образы
make up      # контейнеры, миграции, демоданные
```

После запуска:

| Что | Адрес |
| --- | --- |
| Система | http://localhost:3000 |
| Swagger UI | http://localhost:8000/docs |
| ReDoc | http://localhost:8000/redoc |
| Схема OpenAPI | http://localhost:8000/api/v1/openapi.json |
| Проверка живости | http://localhost:8000/api/v1/health |

В разработке пароля нет: на экране входа выбирается учётная запись.
`petrov` менеджер, `orlova` руководитель, который сам ведёт вузы, `fedorov`
руководитель, `admin` администратор.

## Среды

Состав стенда описан в корневом `docker-compose.yml`, отличия сред лежат
в `cicd/<среда>/`: compose, конфигурация Nginx и пример `.env`.

| Среда | Отличия |
| --- | --- |
| `dev` | система на порту 3000, код API монтируется и перезапускается сам, порты API, PostgreSQL и Keycloak открыты, вход без пароля |
| `preprod` | как боевая, но по HTTP; вход через Keycloak |
| `prod` | HTTPS, наружу только Nginx, несколько процессов API, лимиты памяти, перезапуск при падении |

Секреты задаются файлом `.env` рядом с compose среды (`cicd/prod/.env`).
В репозитории только `.env.example`:

```bash
cp cicd/prod/.env.example cicd/prod/.env   # заполнить пароли
make build ENV=prod && make up ENV=prod
```

В `prod` обязательны `POSTGRES_PASSWORD` и `KEYCLOAK_ADMIN_PASSWORD`. Паролем
консоли Keycloak на новом реалме первый раз входит `admin`, поэтому он должен
проходить политику паролей: от 12 знаков, строчные и заглавные буквы, цифры.
В `preprod` Keycloak работает по HTTP, там задано `KEYCLOAK_SSL_REQUIRED=none`.

Во всех средах наружу смотрит Nginx из образа `edu-crm-web`. Он раздаёт
клиентскую часть, проксирует `/api`, `/docs`, `/redoc`, а в `preprod`
и `prod` ещё и Keycloak.

Одностраничное приложение: после действий страница не перезагружается,
обновляются только затронутые данные. Работает на телефоне.

| Раздел | Что там | Кому |
| --- | --- | --- |
| Главная | своя у каждой роли: у менеджера следующие шаги, у руководителя показатели команды и очередь решений, у администратора обмен, загрузки и очереди проверки | всем |
| Взаимодействия | реестр с фильтрами и карточка: процесс, программы и продукты, договор, контакты, файлы и комментарии, история | менеджеру и руководителю |

| Отчёты и статистика | отчёт по взаимодействиям, статистика обучения, заявки с сайта; XLSX, XLS, PDF, JSON, диаграммы PNG и PDF | менеджеру и руководителю |
| LMS и сайт | синхронизация, загрузка ответа файлом, журнал обмена, очередь сопоставления | администратору и по отдельному праву |
| Администрирование | пользователи и права, загрузка из Excel, рабочие процессы, журнал изменений, настройки | администратору |
| Справочники | направления, программы, вендоры, продукты, шаблоны договоров | администратору и руководителю |

### Клиентская часть в разработке

Нужны Node.js 22 и запущенный API на порту 8000:

```bash
cd frontend
npm ci
npm run dev        # http://localhost:5173
```

Vite проксирует `/api` на `http://localhost:8000` (другой адрес задаёт
`VITE_DEV_API_URL`). Схему входа выбирает сервер через `GET /api/v1/meta/auth`,
поэтому одна сборка работает и с заглушкой, и с Keycloak.

| Команда | Что делает |
| --- | --- |
| `npm run build` | проверка типов и сборка в `dist/` |
| `npm run typecheck`, `npm run lint`, `npm test` | типы, ESLint, тесты Vitest |
| `npm run format` / `format:check` | Prettier |
| `npm run api:types` | типы API из `docs/openapi.json` |
| `npm run theme` | пересобрать тему Ростелекома `src/styles/rt-theme.css` |
| `npm run help:screenshots` | снимки экранов для руководств (нужен Playwright) |

Запросы идут через TanStack Query: ответы кэшируются, после изменения
обновляются только затронутые. Фильтры, выбранные колонки и черновики
комментариев хранятся в `localStorage`, фильтры реестров ещё и в адресе
страницы.

Пакет фирменной темы Atomaro закрытый, поэтому тема повторена файлом
`src/styles/rt-theme.css`: акцентный синий заменён фиолетовым Ростелекома
`#7700FF`. Файл собирает `npm run theme`, руками его не правят.

## API

Схема выводится из моделей и аннотаций, поэтому не расходится с кодом.
`make openapi` выгружает её в `docs/openapi.json`, по нему `npm run api:types`
генерирует типы клиента. CI проверяет, что файл и типы не отстали от кода.

| Раздел | Назначение |
| --- | --- |
| `/me`, `/users` | текущий пользователь с его действиями и областью данных; пользователи, роли, права, доступ к вузам |
| `/dashboard` | главная по роли и поводы вмешаться |
| `/universities`, `/catalog` | вузы и контакты; направления, программы, продукты, вендоры |
| `/interactions` | реестр и карточка взаимодействия, состав, контакты, договор, лицензии, отмена |
| `/interactions/{id}/workflow`, `/start`, `/transition`, `/skip`, `/block` | схема процесса, история, переходы |
| `/interactions/{id}/comments`, `/attachments` | комментарии и файлы |
| `/workflow/templates`, `/workflow/versions` | шаблоны процессов и их версии |
| `/contract-templates` | типовые договоры и проект договора по шаблону |
| `/licenses` | лицензии и сроки |
| `/reports`, `/statistics` | отчёты, выгрузки, диаграммы, статистика обучения |
| `/integrations` | обмен с LMS и сайтом, журнал, очередь сопоставления |
| `/imports` | загрузка каталогов из XLS и XLSX |
| `/audit`, `/settings` | журнал изменений и настройки (администратор) |
| `/meta/enums`, `/meta/auth` | подписи статусов, коды ошибок, схема входа |

Любой отказ возвращает одно тело:

```json
{ "code": "workflow_rule_violated", "message": "Такой переход не предусмотрен...", "details": null }
```

`code` не меняется вместе с текстом, полный список отдаёт `GET /api/v1/meta/enums`.
Интерфейс показывает понятный текст и код, раздел руководства «Если что-то
пошло не так» объясняет, что делать с каждым.

## Роли и права

Роль, функциональные права и область данных разделены
([access.py](backend/app/services/access.py)). Права проверяет сервер в каждом
запросе, интерфейс только прячет недоступные кнопки.

- **Роли не наследуются.** Менеджер ведёт свои взаимодействия, договоры
  и файлы и строит отчёты. Руководитель назначает ответственных, разрешает
  исключения и отменяет взаимодействия команды. Администратору доступны только
  технические функции, бизнес-данных роль не даёт.
- **Отдельные права** выдаёт администратор: запуск обмена, журнал обмена,
  персональные данные студентов, названия этапов.
- **Область данных**: `own` свои взаимодействия и вузы, `team` ещё и команда
  с очередью без ответственного, `all` всё, `none` ничего. По умолчанию
  следует из ролей, её можно задать явно, в том числе временно.
- **Точечный доступ к вузу** со сроком и основанием, например на время
  отпуска коллеги.

В разработке (`AUTH_BACKEND=dev`) пользователь берётся из заголовков:

```bash
curl http://localhost:8000/api/v1/me -H "X-Dev-User: petrov" -H "X-Dev-Roles: manager"
```

### Keycloak

```bash
make keycloak                   # поднять Keycloak и напечатать пароли
AUTH_BACKEND=keycloak make up
```

Реалм `edu-crm` ([realm-export.json](deploy/keycloak/realm-export.json))
содержит роли, клиенты `edu-crm-api` и `edu-crm-web` и 23 пользователя.
Вход только через страницу Keycloak (Authorization Code и PKCE), политика
паролей, защита от подбора и страница входа в стиле Ростелекома включены.
Реалм `master` и консоль Keycloak снаружи закрыты.

Учётными записями управляют на сайте в разделе «Пользователи и права»:
администратор заводит и отключает сотрудников, меняет роли и выдаёт временные
пароли, постоянный пароль сотрудник задаёт сам. Keycloak хранит данные в своей
базе `keycloak` того же PostgreSQL, поэтому обновления стенда их не трогают.
При каждом деплое `keycloak-setup` переносит из выгрузки только настройку
реалма, ролей и клиентов. Пользователей из выгрузки он заводит только в пустой
реалм.

**Паролей в репозитории нет.** Начальный пароль ставится только тому, у кого
его нет: из переменной `KEYCLOAK_USER_PASSWORDS` (пары `логин:пароль` через
запятую), а если войти не может ни один администратор, `admin` получает
временный пароль, равный паролю консоли Keycloak. Сгенерировать пароли:

```bash
cd backend && KEYCLOAK_REALM_FILE=../deploy/keycloak/realm-export.json \
  python -m scripts.keycloak_setup --generate-passwords
```

Идентификаторы пользователей реалма выводятся из логина, поэтому демоданные
заранее знают, кому отдать взаимодействия. Если сменили `AUTH_BACKEND`
после загрузки, выполните `make reset`.

## Рабочий процесс

Процесс и есть взаимодействие (`workflow_instances`). У него статус
(черновик, в работе, заблокировано, завершено, отменено), а у закрытого
результат, причина, автор и время закрытия. Состояния этапов не хранятся,
они вычисляются из истории переходов.

Шаблон версионируется: этапы и переходы принадлежат версии, начатый процесс
идёт по своей версии до конца. У шаблона одна действующая версия,
опубликованную версию менять нельзя (кроме названий этапов и расположения
узлов). Перед публикацией граф проверяется: один старт, достижимый финал,
нет тупиков, циклы только через возвраты. Этапу можно задать обязательные
документы.

В демоданных два шаблона. Основной повторяет 14 шагов из ТЗ:

```
Поиск контактов -> Уточнение программ -> Встреча -> Обмен документами -> [Корректировка] -> Подписание
-> Передача материалов и лицензий -> Сопровождение внедрения -> Обучение преподавателей
-> Актуализация программы -> Ведение занятий -> Актуализация документации
-> Повышение квалификации -> Контроль исполнения
```

Короткий шаблон «Дополнительное соглашение»:

```
Контакт -> Встреча -> Документы -> Согласование -> Подписание
                                        `-> Доработка -> Согласование
```

## Договор по шаблону

Типовой договор ведёт руководитель («Справочники» → «Шаблоны договоров»).
Это текст с полями `{{вуз}}`, `{{инн_вуза}}`, `{{подписант_вуза}}`,
`{{программы}}` и другими. Менеджер формирует по шаблону проект договора:
значения берутся из договора, карточки вуза и взаимодействия, пустые поля
остаются пропусками. Проект скачивается как DOCX или прикладывается
к взаимодействию с типом «Проект договора» и не заменяет подписанный договор.

## Отчёты

Одна выборка даёт и таблицу, и диаграммы, поэтому цифры в них совпадают.

```bash
curl -X POST "http://localhost:8000/api/v1/reports/export?format=xlsx" \
  -H "Content-Type: application/json" \
  -d '{"filters": {"date_from": "2026-01-01"}, "columns": ["university", "program", "stage", "manager"]}' \
  -o report.xlsx
```

- форматы отчёта `xlsx`, `xls`, `pdf`, `json`, диаграммы `png` и `pdf`;
- колонки отдаёт `GET /reports/columns`;
- период считается по началу взаимодействия, движениям процесса, подписанию
  договора или закрытию (`period_basis`);
- строка отчёта: взаимодействие в разрезе одной ИТ-программы, продукты только
  те, что связаны с этой программой.

Выгрузки собираются в очереди с пониженным приоритетом: каждый процесс API
строит не больше `EXPORT_CONCURRENCY` файлов сразу, поэтому десять
одновременных отчётов не тормозят интерфейс.

## Интеграции с LMS и сайтом

Контрактов API LMS и сайта организаторы не дали, поэтому пока адрес источника
не задан, адаптер берёт тестовый ответ из
[fixtures](backend/app/services/integrations/fixtures). Формат записей взят
из выгрузок кейсодержателя. Для настоящего API достаточно задать
`LMS_BASE_URL`, `SITE_BASE_URL` и токены, при другом формате меняется только
разбор ответа в адаптере. Выгрузку можно загрузить и файлом JSON.

- справочники обновляются, новые вузы приходят «На проверке»;
- заявка вуза попадает в открытое взаимодействие с ним или заводит черновик;
- заявка студента идёт только в статистику;
- запись, похожую на существующую, система не сопоставляет по названию,
  а кладёт в очередь ручного сопоставления;
- ошибка одной записи не останавливает обмен, запуск получает статус
  «частично»;
- повторный обмен дублей не создаёт, связь с внешней записью хранится
  в `external_links`;
- из анкет LMS не сохраняются паспорт, СНИЛС, адрес и диплом (152-ФЗ).

Сбои сети и ответы 5xx повторяются до трёх раз. Обмен по расписанию включает
администратор в «Настройках», в нескольких процессах API он выполняется
один раз благодаря блокировке в PostgreSQL.

## Импорт каталогов

Порядок: файл, сопоставление колонок, проверка, импорт, итог «создано,
обновлено, отклонено». Проверка выполняет загрузку целиком и откатывает её,
поэтому заранее показывает точный итог. Колонки узнаются по заголовкам
и синонимам, строка с ошибкой отклоняется целиком. Образец с нужными
заголовками:

```bash
curl -o template.xlsx "http://localhost:8000/api/v1/imports/template?type=catalog"
```

Сводный каталог загружается через модель взаимодействия: строка становится
взаимодействием с договором, продукт привязывается к ИТ-программе, лицензия
к договору. Вуз ищется по ИНН, без ИНН по названию.

## Контроль проблемных процессов

`GET /api/v1/dashboard/alerts` собирает поводы вмешаться: этап дольше нормы,
процесс заблокирован или не запущен, заканчивается договор или лицензия,
нет ответственного или обязательного документа, не начато внедрение.
Администратору ещё и технические: ошибки обмена, очередь сопоставления,
вузы на проверке.

Те же поводы показывает колокольчик. Прочитанное уходит со счётчика,
а проблема остаётся на главной, пока её не решат. Блокировки и просрочки,
которые уже видны в следующих шагах или очереди решений, в «Требует
внимания» не повторяются, их число отдаёт поле `alerts_in_steps`.

## Кэш

Главная, поводы и отчёты кэшируются на сервере и сбрасываются при любом
изменении данных: в базе есть общий счётчик версии данных. Клиент тоже
кэширует ответы и помнит фильтры между сеансами (требование 13 ТЗ).

## Условия и ограничения

- **XLS** это настоящий Excel 97, в него попадает не больше 65 000 строк.
  Полный набор выгружается в XLSX.
- **PDF** содержит не больше 1000 строк. Для кириллицы нужен шрифт DejaVu,
  он ставится в образ.
- **Файлы**: png, jpeg, pdf, zip, gzip, rar, doc, docx, xls, xlsx, размер
  до `MAX_UPLOAD_MB` (25 МБ). Содержимое лежит на диске, в базе только путь.
- **Договор** у взаимодействия необязательный, один на взаимодействие.
- **Интеграции** работают на тестовых ответах и загрузке файлом, пока
  не заданы адреса настоящих API.
- **Договор по шаблону** без таблиц и картинок, значения подставляются
  без склонения.

## Боевой стенд

Стенд https://edu-crm.nikitarodionov.ru обновляется сам: пуш в `main`
запускает CI, после зелёного CI workflow «Деплой» выкладывает ровно
проверенный коммит. Красный CI до сервера не доходит.

Что делает деплой:

1. Собирает образы API и Nginx с клиентской частью на раннере GitHub.
   Образ Keycloak собирается, только если изменился `deploy/keycloak/image`.
2. Проверяет секрет `PROD_ENV` и подключается по SSH с проверкой ключа хоста.
3. Готовит сервер (`bootstrap.sh`): Docker, certbot, swap, ротация логов,
   ежедневные копии. Повторный запуск ничего не ломает.
4. Кладёт код в новый каталог релиза и привозит образы.
5. Выпускает сертификат, если его нет.
6. Поднимает релиз (`release.sh activate`): миграции, настройка Keycloak,
   демоданные в пустую базу. Если релиз не поднялся, возвращается прежний.
7. Проверяет стенд снаружи: HTTPS, клиентскую часть, API, Keycloak,
   заголовки безопасности.

Секреты репозитория:

| Секрет | Что в нём |
| --- | --- |
| `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY` | адрес сервера, пользователь деплоя и его ключ |
| `SSH_KNOWN_HOSTS` | ключ хоста: `ssh-keyscan <SSH_HOST>` |
| `PROD_ENV` | содержимое `.env` боевой среды, образец `cicd/prod/.env.example` |
| `KEYCLOAK_USER_PASSWORDS` | необязательно: начальные пароли при создании реалма |

На сервере:

```
/opt/edu-crm/
  releases/<дата>-<коммит>/   код релиза, в REVISION коммит и запуск Actions
  current -> releases/...      текущий релиз
  shared/prod.env              секрет PROD_ENV
  backups/                     резервные копии за 14 дней
```

Данные лежат в томах Docker (`edu-crm_pgdata`, `edu-crm_api_storage`),
релизы и откаты их не трогают. Хранятся 5 последних релизов.

Логи и состояние:

```bash
cd /opt/edu-crm/current
cat REVISION                                  # какой коммит выложен
make logs ENV=prod                            # логи API
bash cicd/prod/server/release.sh compose ps   # контейнеры
docker stats --no-stream                      # память и процессор
```

Откат:

```bash
bash cicd/prod/server/release.sh list       # релизы, * текущий
bash cicd/prod/server/release.sh rollback   # на предыдущий удачный
```

Можно и через GitHub: Actions → «Деплой» → Run workflow с нужным коммитом.
Чтобы следующий пуш не вернул плохую версию, её отменяют через `git revert`.
Миграции откат кода не откатывает.

Сертификат Let's Encrypt продлевает `certbot.timer`, проверочные файлы отдаёт
Nginx, стенд при этом не останавливается. Проверка: `sudo certbot renew --dry-run`.

### Резервные копии

Каждую ночь `edu-crm-backup.timer` снимает копию базы системы, базы Keycloak
и файлов вложений в `/opt/edu-crm/backups`, копии хранятся 14 дней.
Их стоит забирать за пределы сервера. Копия вручную:
`bash cicd/prod/server/release.sh backup`.

Восстановление (ДАТА из имени файла):

```bash
cd /opt/edu-crm/current
R="bash cicd/prod/server/release.sh"
$R compose stop api keycloak nginx
$R compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --clean --if-exists --no-owner' \
  < ../../backups/ДАТА-edu_crm.dump
$R compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d keycloak --clean --if-exists --no-owner' \
  < ../../backups/ДАТА-keycloak.dump
$R compose up -d --wait --no-build
$R compose exec -T api sh -c 'rm -rf /app/storage/* && tar xzf - -C /app/storage' \
  < ../../backups/ДАТА-storage.tgz
```

### Нагрузка и память

Сервер: 2 vCPU и 4 ГБ. Под нагрузкой из ТЗ (50 пользователей и 10 отчётов
одновременно) стенд занимает около 1,4 ГБ: API с 4 процессами около 550 МБ,
Keycloak около 560 МБ, PostgreSQL около 220 МБ. Если памяти мало, уменьшите
`WEB_CONCURRENCY` до 2.

Замер на сервере. Вход по паролю для замера включается отдельным клиентом
Keycloak только на это время:

```bash
cd /opt/edu-crm/current
R="bash cicd/prod/server/release.sh"
$R keycloak-setup --loadtest on
export KEYCLOAK_USER_PASSWORDS="менеджер:пароль,руководитель:пароль"
make loadtest ENV=prod ARGS="--keycloak-url http://keycloak:8080"
$R keycloak-setup --loadtest off
```

## Тесты и CI

```bash
make test     # тесты
make check    # стиль, тесты, сверка моделей с миграциями
```

Тесты API работают с отдельной базой `edu_crm_test`, которая пересоздаётся
перед каждым тестом. Без PostgreSQL они пропускаются. Тесты клиентской части:
`npm test` в `frontend/`.

[CI](.github/workflows/ci.yml) запускается на каждый push и pull request:

- **Тесты и стиль**: Ruff, тесты с PostgreSQL, миграции, демоданные,
  актуальность `docs/openapi.json`;
- **Клиентская часть**: типы API, TypeScript, ESLint, Prettier, тесты, сборка;
- **Сборка образов**: API, Nginx, Keycloak, конфигурации сред, shellcheck.

## Запуск без Docker

Нужен свой PostgreSQL.

```bash
cd backend
python -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env              # указать свой PostgreSQL
alembic upgrade head
python -m scripts.seed
uvicorn app.main:app --reload
```

Клиентская часть: `cd frontend && npm ci && npm run dev`, откроется
на http://localhost:5173.
