# Система контроля взаимодействия ИТ Школы Ростелекома с вузами

Веб-система для ИТ Школы Ростелекома. Центральный объект —
**взаимодействие с вузом**: у него вуз, ответственный менеджер, рабочий
процесс по шагам, ИТ-программы и связанные с ними ИТ-продукты, контакты,
файлы и история, а договор с лицензиями — необязательная часть, которая
появляется, когда работа до неё дойдёт. Кроме того — отчёты и статистика
обучения, обмен с LMS и сайтом, загрузка каталогов из Excel.

- Боевой стенд — https://edu-crm.nikitarodionov.ru (API — `/docs`)
- Соответствие ТЗ по пунктам — [docs/requirements.md](docs/requirements.md)
- Библиотеки и версии — [docs/libraries.md](docs/libraries.md)
- Архитектура в Archi — [docs/architecture](docs/architecture/README.md)
- Решения по бизнес-модели — [docs/business-model-decisions.md](docs/business-model-decisions.md),
  перечень исправлений и их статус — [docs/required-fixes.md](docs/required-fixes.md)
- Руководства менеджера, руководителя, администратора и системного
  администратора встроены в систему: раздел «Руководства»

## Запуск

Нужны только Docker и make.

```bash
make build   # собрать образы и подготовить проект
make up      # запустить: контейнеры, миграции, демоданные
```

Дальше:

- Система — http://localhost:3000. В разработке пароля нет: на экране входа
  выберите учётную запись (`petrov` — менеджер, `orlova` — руководитель,
  который и сам ведёт вузы, `fedorov` — руководитель, `admin` —
  администратор)
- Swagger UI — http://localhost:8000/docs
- OpenAPI — http://localhost:8000/api/v1/openapi.json
- Проверка живости — http://localhost:8000/api/v1/health

`make down` останавливает стенд, `make reset` — сносит вместе с данными
и собирает заново. Клиентскую часть с горячей перезагрузкой запускает
`npm run dev` — см. [frontend/README.md](frontend/README.md).

## Среды

Состав стенда описан в корневом `docker-compose.yml` и одинаков везде;
отличия сред лежат в `cicd/<среда>/docker-compose.yml`:

| Среда | Отличия |
| --- | --- |
| `dev` | система на порту 3000, код API монтируется, сервер перезапускается сам, порты открыты, авторизация — заглушка |
| `preprod` | как на бою, но по HTTP; наружу смотрит Nginx; авторизация через Keycloak |
| `prod` | HTTPS, несколько рабочих процессов, ограничения памяти, перезапуск при падении |

Секреты задаются файлом `.env` рядом с конфигурацией среды
(`cicd/prod/.env`), в репозиторий он не попадает — есть только `.env.example`.

Боевой стенд https://edu-crm.nikitarodionov.ru обновляется сам после
зелёного CI на `main`: как устроен деплой, где смотреть логи и как
откатиться — в [cicd/README.md](cicd/README.md#боевой-стенд-автоматический-деплой).

## Зависимости

`backend/requirements.txt` задаёт диапазоны версий, `backend/requirements.lock` —
снимок того, что реально стоит в собранном образе, вместе с зависимостями
зависимостей. Dockerfile ставит из lock, если файл есть, поэтому сборка
повторяется один в один. После правки `requirements.txt`:

```bash
make build && make lock
```

Клиентская часть ставится строго по `frontend/package-lock.json` (`npm ci`).

## Интерфейс

Одностраничное приложение: страница не перезагружается, после действия
обновляются только затронутые данные. Разделы бокового меню:

| Раздел | Что там | Кому |
| --- | --- | --- |
| Главная | своя у каждой роли: у менеджера — «Следующие шаги» (статус, этап со следующим действием и срок этапа отдельными блоками), у руководителя — показатели команды, очередь решений, нагрузка менеджеров, у администратора — обмен, загрузки, очереди проверки | всем |
| Взаимодействия | реестр с фильтрами; карточка: «Сведения» и «Обзор взаимодействия», вкладки «Процесс», «Программы и продукты», «Договор», «Контакты», «Файлы и комментарии», «История» | менеджеру и руководителю |
| Вузы | список и карточка вуза, контакты вуза, проверка новых вузов и объединение дублей | менеджеру — вузы своей области; руководителю и администратору — справочник целиком |
| Отчёты и статистика | отчёт по взаимодействиям, статистика обучения, заявки с сайта (по отдельному праву); выгрузки XLSX, XLS, PDF, JSON, диаграммы PNG и PDF | менеджеру и руководителю |
| LMS и сайт | источники, синхронизация, загрузка ответа файлом JSON, журнал обмена, очередь сопоставления | администратору и по отдельному праву |
| Пользователи и права, Загрузка из Excel, Рабочие процессы, Журнал изменений, Настройки | администрирование | администратору |
| Справочники | направления, программы, вендоры, продукты; продукты программ задаёт руководитель | администратору и руководителю |

## Документация API

Схема описывается не отдельным файлом, а выводится из моделей и аннотаций,
поэтому не расходится с кодом:

- Swagger UI — http://localhost:8000/docs
- ReDoc — http://localhost:8000/redoc
- схема — http://localhost:8000/api/v1/openapi.json

Для клиентской части схема выгружается в файл: `make openapi` кладёт её
в [docs/openapi.json](docs/openapi.json), по нему генерируются типы
клиента (`npm run api:types`). CI сверяет и файл с кодом, и типы
с файлом — изменение API без обновления схемы и типов не пройдёт.

Описания отказов общие для всех методов и собраны в одном месте
([app/api/openapi.py](backend/app/api/openapi.py)): в Swagger у каждого
метода видно и формат тела ошибки, и список кодов.

## Авторизация и права

`AUTH_BACKEND=dev` (по умолчанию) включает заглушку: токен не проверяется,
пользователь берётся из заголовков запроса. Интерфейс в этом режиме
показывает список учётных записей вместо формы входа.

```bash
curl http://localhost:8000/api/v1/me \
  -H "X-Dev-User: petrov" \
  -H "X-Dev-Roles: manager"
```

Роли: `manager` (Менеджер), `head` (Руководитель), `admin`
(Администратор). Без заголовков подставляется пользователь из `DEV_USER_*`
со всеми ролями.

Роль, функциональные права и область данных разделены
([app/services/access.py](backend/app/services/access.py)):

- **роли не наследуются** — у каждой свой набор действий, совмещение
  задаётся несколькими ролями явно:
  - **менеджер** заводит взаимодействия и становится ответственным, ведёт
    процесс, программы и продукты, договор и лицензии, контакты, файлы;
    предлагает новые вузы; строит отчёты;
  - **руководитель** назначает ответственных, пропускает обязательные
    этапы, принимает исключения по продуктам, отменяет взаимодействия
    команды, подтверждает вузы и объединяет дубли, задаёт продукты
    ИТ-программ;
  - **администратор** — только технические функции: пользователи и права,
    справочники, загрузка из Excel, шаблоны процессов, обмен с LMS
    и сайтом, журнал изменений, настройки. Бизнес-данных роль не даёт;
- **отдельные права** сверх роли выдаёт администратор: запуск обмена,
  журнал обмена, персональные данные студентов, названия этапов
  и расположение схемы;
- **область данных**: `own` — свои взаимодействия и вузы, `team` — ещё
  и команда (менеджеры, у которых сотрудник руководитель) и очередь
  без ответственного, `all` — всё, `none` — ничего. По умолчанию
  следует из ролей, её можно задать явно — в том числе временно,
  с основанием и сроком;
- **точечный доступ к вузу** — со сроком, основанием, отметкой, кто
  выдал и кто отозвал.

`GET /me` возвращает готовый список действий (`actions`) и действующую
область (`effective_scope`). Права проверяются сервером в каждом запросе,
интерфейс лишь прячет недоступные кнопки. Запись пользователя находится в каждом запросе,
поэтому отключённая учётная запись не выполнит ни одного действия,
а любое изменение попадает в журнал от имени автора.

Демоданные заводятся под ту схему входа, что настроена при загрузке:
под dev-заглушкой это `petrov` (14 взаимодействий, 5 поводов в «Требует
внимания»), `orlova` — руководитель команды и сама менеджер, `fedorov` —
руководитель с временно открытой областью «все». Кто есть в системе
и что показывать, описано в [testdata/README.md](testdata/README.md).

### Keycloak

```bash
make keycloak                   # поднимет Keycloak, перенесёт реалм, напечатает пароли
AUTH_BACKEND=keycloak make up    # или задайте переменную в .env
```

Реалм `edu-crm` ([deploy/keycloak/realm-export.json](deploy/keycloak/realm-export.json))
содержит роли, клиент `edu-crm-api` (аудитория токена), публичный клиент
`edu-crm-web` для интерфейса и 23 пользователя: 20 менеджеров
(`petrov`, `ivanova`, …), руководители `orlova` (ещё и менеджер)
и `fedorov`, администратор `admin`. Интерфейс входит только через страницу Keycloak (Authorization
Code + PKCE): выдача токена по паролю в обход неё у `edu-crm-web`
выключена. Включены политика паролей (от 12 знаков, строчные, заглавные
и цифры, не совпадает с логином), защита от подбора, журнал входов
и страница входа в стиле Ростелекома (тема
[deploy/keycloak/image/themes/edu-crm](deploy/keycloak/image/themes/edu-crm)).

**Учётными записями управляют на сайте**, в разделе «Пользователи
и права»: администратор заводит и отключает сотрудников, меняет роли
и выдаёт временные пароли. Постоянный пароль сотрудник придумывает сам:
Keycloak просит об этом при первом входе с временным паролем, а сменить
его потом можно в меню → «Учётная запись» → «Сменить пароль». Обновления стенда
этих изменений не трогают. Сотрудников не удаляют, а отключают: за ними
остаются взаимодействия и история.

Переход на модель без наследования ролей `keycloak-setup` выполняет сам,
один раз (отметка — атрибут реалма `eduCrmRoleModel`): учётке из выгрузки,
у которой остались роли старой иерархии (администратору добавляли
`manager` и `head`, руководителю — `manager`), ставятся роли новой
выгрузки. Роли, изменённые на сайте, и учётки, заведённые там, не
трогаются.

Keycloak собран под PostgreSQL и хранит данные в своей базе `keycloak`
того же сервера PostgreSQL, поэтому пересоздание контейнера ничего не
сбрасывает. Из выгрузки реалма берутся:

- **настройка** — параметры реалма, роли и клиенты. Её переносит
  в работающий Keycloak разовая задача `keycloak-setup`
  ([scripts/keycloak_setup.py](backend/scripts/keycloak_setup.py)),
  её запускают `make up` в preprod и prod и деплой. Адреса возврата
  после входа — адреса интерфейса этой среды из `CORS_ORIGINS`;
- **учётные записи** — только при создании реалма на пустой базе
  Keycloak. Дальше их ведут на сайте, и удалённый или отключённый там
  сотрудник с обновлением не вернётся.

**Паролей в репозитории нет.** У пользователей из выгрузки пароля нет,
и `keycloak-setup` ставит начальный пароль только тому, у кого его ещё нет,
то есть сразу после создания реалма:

- из переменной `KEYCLOAK_USER_PASSWORDS`, если она задана, — пары
  `логин:пароль` через запятую; на боевом стенде это необязательный
  секрет репозитория. Нужен только при создании реалма, потом его можно
  удалить;
- если войти не может ни один администратор, `admin` получает временный
  пароль, равный паролю консоли Keycloak (`KEYCLOAK_ADMIN_PASSWORD`):
  Keycloak попросит сменить его при первом входе, а пароли остальным
  администратор задаст на сайте;
- в разработке (`make keycloak`) недостающие пароли генерируются
  и печатаются в консоль.

Сгенерировать стойкие пароли для всех пользователей выгрузки:

```bash
cd backend && KEYCLOAK_REALM_FILE=../deploy/keycloak/realm-export.json \
  python -m scripts.keycloak_setup --generate-passwords
```

Внешний и внутренний адреса Keycloak разные: издатель токена проверяется
по `KEYCLOAK_BASE_URL` (так Keycloak видит браузер), а ключи реалма API
забирает по `KEYCLOAK_INTERNAL_URL` (имя контейнера). Снаружи, через Nginx,
открыт только реалм `edu-crm`: реалм `master` и консоль администратора
Keycloak из интернета недоступны.

У пользователей реалма фиксированные `id`, они выводятся из логина
([scripts/demo/people.py](backend/scripts/demo/people.py)). Поэтому сид,
запущенный с `AUTH_BACKEND=keycloak`, заранее знает, кому отдать
взаимодействия: `petrov`, войдя через Keycloak, видит свои. Под
dev-заглушкой те же пользователи получают идентификатор `dev:<логин>`.
Если сменили `AUTH_BACKEND` после загрузки, выполните `make reset`. Новый
пользователь Keycloak заводится в базе при первом обращении,
взаимодействия ему назначает руководитель. ФИО из токена берётся только при первом входе: дальше им
распоряжается CRM, потому что в отчётах нужно полное ФИО.

Обе схемы реализуют один интерфейс `AuthBackend`
([app/core/security.py](backend/app/core/security.py)), остальной код
про разницу не знает.

## Ошибки

Любой отказ возвращает одно и то же тело — требование о кодах ошибок
из нефункциональных требований ТЗ:

```json
{ "code": "workflow_rule_violated", "message": "Такой переход не предусмотрен...", "details": null }
```

`code` машиночитаем и не меняется вместе с текстом сообщения. Полный
список — в `GET /api/v1/meta/enums`. Интерфейс показывает понятный текст
и код, а раздел руководства «Если что-то пошло не так» объясняет, что
делать с каждым.

## Рабочий процесс

Процесс — это само взаимодействие (`workflow_instances`): у него статус
(черновик, в работе, заблокировано, завершено, отменено), а у закрытого —
результат (успешно, частично, неуспешно), причина, комментарий, автор
и время закрытия. Завершение — переход на финальный этап, у которого
задан результат; досрочное прекращение — отмена с причиной.

Шаблон версионируется: этапы и переходы принадлежат версии
(`workflow_versions`), экземпляр процесса жёстко привязан к своей версии.
Жизненный цикл версии: черновик → действующая → устаревшая (по ней
доходят начатые процессы) → выведена из использования. База гарантирует
одну действующую версию на шаблон, а триггер — неизменность опубликованной
версии. Исключения — координаты узлов схемы и названия этапов
(по отдельному праву, требование 2 ТЗ).

Перед публикацией граф проверяется: ровно один стартовый этап,
у финальных этапов задан результат и нет исходящих переходов, нет тупиков
и недостижимых этапов, из старта достижим финал, циклы — только через
переходы-возвраты. У этапа можно задать обязательные типы документов
(без них вперёд не уйти) и статусы программ и продуктов при входе.

Состояния этапов (не начат, активен, завершён, пропущен, заблокирован)
нигде не хранятся — они вычисляются из истории переходов
(`workflow_events`) и текущего этапа экземпляра.

В демоданных два шаблона ([scripts/demo/processes.py](backend/scripts/demo/processes.py)).

Основной шаблон — это 14 шагов базового workflow из ТЗ, от поиска контактов
до контроля исполнения. «Корректировка документов» в нём необязательна.
Шаблон существует в двух версиях: во второй необязательным стало и
повышение квалификации. Взаимодействия, начатые до выхода второй версии,
идут по первой.

```
Поиск контактов -> Уточнение программ -> Встреча -> Обмен документами -> [Корректировка] -> Подписание
-> Передача материалов и лицензий -> Сопровождение внедрения -> Обучение преподавателей
-> Актуализация программы -> Ведение занятий -> Актуализация документации
-> Повышение квалификации -> Контроль исполнения
```

Короткий шаблон «Дополнительное соглашение» — маршрут из концепции:

```
Контакт -> Встреча -> Документы -> Согласование -> Подписание
                                        `-> Доработка -> Согласование
```

| Метод | Назначение |
| --- | --- |
| `GET /api/v1/interactions/{id}/workflow` | схема, состояния этапов, история, доступные переходы |
| `POST /api/v1/interactions/{id}/start` | запустить процесс черновика со стартового этапа |
| `POST /api/v1/interactions/{id}/transition` | перейти на разрешённый этап; на финальный — с причиной, если результат неуспешный |
| `POST /api/v1/interactions/{id}/skip` | пропустить необязательный этап с причиной |
| `POST /api/v1/interactions/{id}/block`, `/unblock` | заблокировать процесс и снять блокировку |
| `POST /api/v1/interactions/{id}/cancel` | отменить взаимодействие с причиной |
| `PATCH /api/v1/workflow/stages/{id}` | переименовать этап (отдельное право) |
| `PUT /api/v1/workflow/versions/{id}/graph` | сохранить схему черновика |
| `POST /api/v1/workflow/versions/{id}/publish` | опубликовать версию |

## Отчёты и диаграммы

Фильтры передаются телом запроса, одна выборка даёт и таблицу, и диаграммы —
поэтому цифры в них всегда совпадают.

```bash
curl -X POST "http://localhost:8000/api/v1/reports/export?format=xlsx" \
  -H "Content-Type: application/json" \
  -d '{"filters": {"date_from": "2026-01-01"}, "columns": ["university", "program", "stage", "manager"]}' \
  -o report.xlsx
```

- форматы отчёта: `xlsx`, `xls`, `pdf`, `json`;
- форматы диаграммы (`POST /reports/chart`, `POST /statistics/chart`): `png`, `pdf`;
- доступные колонки: `GET /reports/columns`;
- период считается по дате начала взаимодействия, движениям процесса,
  подписанию договора или закрытию — параметр `period_basis`. По дате
  подписания в отчёт входят только подписанные договоры, число
  неподписанных показывается отдельно: дата создания её не подменяет;
- фильтры по статусу и результату взаимодействия, причине закрытия,
  источнику, статусу договора, этапам, вузам, программам, продуктам,
  ответственным.

Строка отчёта — это взаимодействие в разрезе одной ИТ-программы,
в ячейке «ИТ-продукт» — только продукты, фактически связанные с этой
программой во взаимодействии. Договор — один из атрибутов строки.
Итоги считаются по идентификаторам, а не по названиям.

Выгрузки собираются в очереди с пониженным приоритетом
([services/export/runner.py](backend/app/services/export/runner.py)):
каждый процесс API строит не больше `EXPORT_CONCURRENCY` файлов
одновременно (по умолчанию 1), остальные ждут. Так десять одновременных
отчётов не отнимают процессор у интерфейса.

## Интеграции

Контрактов API LMS и сайта пока нет, поэтому между внешней системой
и остальным кодом стоит адаптер. Формат записей взят из данных
кейсодержателя: заявки сайта («Номер заявки», «Курс», ФИО, телефон,
почта, «Номер потока») и анкеты LMS. Пока адрес источника не задан,
адаптер отвечает тестовыми данными из
[fixtures](backend/app/services/integrations/fixtures); выгрузку можно
загрузить и файлом JSON (`POST /integrations/sources/{code}/upload`).
При появлении реального контракта меняется только разбор ответа внутри
адаптера.

```bash
curl -X POST http://localhost:8000/api/v1/integrations/sync
```

Синхронизация ([services/integrations/sync.py](backend/app/services/integrations/sync.py)):

- обновляет справочники; новые вузы приходят «На проверке»;
- заявка вуза на сотрудничество добавляется в открытое взаимодействие
  с этим вузом или заводит взаимодействие-черновик — договор обмен
  не создаёт, процесс запускает ответственный;
- заявка студента — только статистика: заявка, поток (стабильный ключ
  и период) и зачисление на программу; взаимодействие она не создаёт;
- запись без связи, но с похожей записью в системе, по одному названию
  не сопоставляется, а попадает в очередь ручного сопоставления;
- ошибка отдельной записи не роняет обмен: запуск получает статус
  «частично», ошибка — строку в журнале запуска.

Повторный запуск дублей не создаёт: связь с внешней записью хранится
в `external_links`, идентификатор уникален в пределах источника и типа
записи. Из анкет LMS сохраняются только ФИО, контакты, пол, образование
и регион — паспорт, СНИЛС, адрес и сведения о дипломе отбрасываются
(152-ФЗ), что записывается в журнал обмена.

Промышленный режим ([scheduler.py](backend/app/services/integrations/scheduler.py)):
адреса и токены — `LMS_BASE_URL`, `LMS_TOKEN`, `SITE_BASE_URL`,
`SITE_TOKEN`; сбой сети и ответы 5xx повторяются до трёх раз с паузой;
обмен по расписанию — раз в N часов по настройке администратора
(`INTEGRATION_SYNC_INTERVAL_HOURS` — значение по умолчанию, 0 — только
вручную), один раз на все рабочие процессы API благодаря
рекомендательной блокировке PostgreSQL. Курсор выгрузки и правила
удаления записей зависят от контракта API источника: пока источник
отдаёт полный снимок, пропавшие из него записи не удаляются.

## Импорт каталогов

Порядок работы: файл → предпросмотр с сопоставлением колонок → проверка
→ импорт → итог «создано / обновлено / отклонено». Проверка выполняет
загрузку целиком и откатывает её, поэтому заранее показывает точный итог
и все ошибки, ничего не записывая.

```bash
# образец с нужными заголовками
curl -o template.xlsx "http://localhost:8000/api/v1/imports/template?type=catalog"
```

Типы загрузок: сводный каталог (все поля из требования 1 ТЗ), вузы,
ответственные от вузов, ИТ-программы, ИТ-продукты, вендоры с их
контактами, анкеты обучающихся из LMS. Колонки узнаются по заголовкам
и синонимам, сопоставление можно поправить вручную. Строка с ошибкой
отклоняется целиком: каждая строка пишется в своей точке сохранения.

Сводный каталог загружается через модель взаимодействия: строка —
взаимодействие с вузом и его договор, продукт — только вместе
с ИТ-программой, лицензия — по договору на этот продукт. Вуз узнаётся
по ИНН, а без ИНН — по названию; новый вуз из файла ждёт проверки.

## Контроль проблемных процессов

`GET /api/v1/dashboard/alerts` собирает взаимодействия, по которым
требуется действие: этап дольше нормы (`sla_days` этапа), процесс
заблокирован или не запущен, заканчивается срок договора или лицензии,
не назначен ответственный, нет обязательных документов, не начато
внедрение, продукт не связан с программой. Администратору — технические
поводы: ошибка синхронизации, записи в очереди сопоставления, вузы
на проверке. Для каждого случая видны причина, ответственный и сколько
времени ситуация не меняется.

## Кэш

Сводки на главной, тревоги и выборки отчётов кэшируются на сервере
и сбрасываются при любом изменении данных (счётчик версии данных в базе,
общий для всех процессов API). Клиент кэширует ответы и обновляет их
в фоне, а фильтры, выбранные колонки и черновики комментариев помнит
между сеансами — требование 13 ТЗ.

## Условия и ограничения

- **Формат xls.** Отчёт `format=xls` — настоящий двоичный Excel 97 (xlwt).
  У формата предел 65 535 строк, поэтому в XLS попадает не больше
  65 000 строк, полный набор — в XLSX. Загрузка файлов `.xls` тоже
  поддерживается — их читает xlrd.
- **PDF.** Кириллица требует шрифта DejaVu; в образе он ставится пакетом
  `fonts-dejavu-core`. Если шрифт не найден, отчёт формируется стандартным
  Helvetica, о чём пишется предупреждение в лог. В PDF попадает не больше
  1000 строк, полный набор данных — в XLSX.
- **Файлы.** Допустимые форматы вложений — png, jpeg, pdf, zip, gzip, rar,
  doc, docx, xls, xlsx; ограничение размера — `MAX_UPLOAD_MB` (25 МБ).
  Содержимое лежит на диске, в базе — только путь и сведения о файле.
- **Модель.** Взаимодействие — центральный объект, договор у него
  необязательный (0..1). У программы — статус внедрения, у продукта —
  статус передачи; продукт во взаимодействии всегда связан хотя бы
  с одной программой.
- **Статусы** договоров, лицензий, программ и продуктов (`app/enums.py`)
  согласованы в [решениях по бизнес-модели](docs/business-model-decisions.md).
- **Интеграции** работают на тестовых ответах и загрузке файлом, пока
  организаторы не передали контракты API; расписание, повторы,
  идемпотентность и журнал ошибок готовы к реальным адресам.

## Проверки при изменениях

[GitHub Actions](.github/workflows/ci.yml) запускается на каждый push
и pull request:

- **Тесты и стиль** — Ruff (проверка и форматирование), тесты
  с PostgreSQL, миграции, сверка моделей с миграциями, загрузка
  демоданных, актуальность `docs/openapi.json`;
- **Клиентская часть** — актуальность типов API, TypeScript, ESLint,
  Prettier, тесты, сборка;
- **Сборка образов** — образы API, Nginx с клиентской частью и Keycloak,
  проверка конфигураций сред и скриптов сервера (shellcheck).

Результат виден галочкой у коммита и блоком Checks в pull request,
итог прогона тестов — на странице проверки.

Чтобы ветку нельзя было слить с падающими проверками, в настройках
репозитория включается Settings → Branches → Add rule для `main`:
«Require status checks to pass before merging» и отметить проверки
«Тесты и стиль», «Клиентская часть» и «Сборка образов».
