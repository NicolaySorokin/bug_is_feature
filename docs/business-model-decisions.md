# Решения по бизнес-модели

Рабочий документ бизнес- и системного анализа проекта. Здесь фиксируются согласованные решения, допущения и открытые вопросы.

## 1. Взаимодействие с вузом и workflow

### Решение

- Конкретный экземпляр workflow (`WorkflowInstance`) трактуется как взаимодействие с вузом.
- Шаблон workflow описывает типовой процесс, например «Классический процесс».
- Экземпляр создаётся для конкретного вуза по зафиксированной версии шаблона.
- Договор появляется в ходе взаимодействия и не должен быть обязательным условием запуска процесса.

### Целевая связь

```text
Вуз 1 -> N Взаимодействий / WorkflowInstance
WorkflowInstance N -> 1 WorkflowVersion
WorkflowInstance 0 -> 1 Договор
```

У одного вуза может быть несколько взаимодействий: последовательных или параллельных по разным инициативам. Каждое взаимодействие в MVP ведёт максимум к одному договору.

### Следствие для текущей реализации

Текущая обязательная привязка `WorkflowInstance` к договору требует пересмотра. Заявка с сайта должна создавать взаимодействие, а не фиктивный договор-черновик.

## 2. Сущности workflow

```text
WorkflowTemplate
└── WorkflowVersion
    ├── WorkflowStage
    ├── WorkflowTransition
    └── WorkflowInstance
        └── WorkflowEvent
```

- `WorkflowTemplate` — тип процесса.
- `WorkflowVersion` — конкретная редакция шаблона.
- `WorkflowStage` — этап процесса.
- `WorkflowTransition` — разрешённый переход между этапами.
- `WorkflowInstance` — конкретное взаимодействие с вузом.
- `WorkflowEvent` — история действий и переходов.
- Состояния этапов вычисляются из текущего этапа и истории событий, отдельно не хранятся.

## 3. Жизненный цикл версии шаблона

### Решение

```text
draft -> active -> deprecated -> retired
```

| Состояние | Назначение |
| --- | --- |
| `draft` | Черновик, можно редактировать, нельзя запускать процессы |
| `active` | Единственная действующая версия для новых процессов |
| `deprecated` | Новые процессы не запускаются, существующие продолжаются |
| `retired` | Активных процессов не осталось, версия хранится для истории |

### Правила

- Для одного шаблона допускается не более одной версии `active`.
- Пользователь выбирает шаблон, а система автоматически назначает его активную версию.
- Экземпляр навсегда фиксирует `workflow_version_id`.
- Публикация нового черновика переводит прежнюю активную версию в `deprecated`.
- После завершения последнего активного процесса устаревшая версия переводится в `retired`.
- Опубликованные версии нельзя структурно изменять или удалять.
- Для отката создаётся новая версия на основе старой; старая версия повторно не активируется.
- Фактическое использование версии определяется количеством связанных экземпляров, а не ручным статусом.

## 4. Открытые вопросы

1. Допускаются ли параллельные взаимодействия одного типа с одним вузом?
2. Кто вправе отменять взаимодействие и можно ли его возобновлять?
3. Какие данные программ и продуктов фиксируются до появления договора?

## 5. Вуз, взаимодействие и договор

### Решение для MVP

```text
Вуз 1 -> N Взаимодействий / WorkflowInstance
Взаимодействие 0 -> 1 Договор
```

- Вуз — постоянный контрагент и хранит общую историю сотрудничества.
- Взаимодействие — отдельная инициатива с собственным началом, ответственным, программами, продуктами и workflow.
- Договор — самостоятельная юридическая сущность, возникающая в ходе взаимодействия.
- До подписания договор может отсутствовать либо существовать как черновик внутри взаимодействия.
- Подписание договора является этапом основного workflow; отдельный workflow договора в MVP не нужен.
- Несколько договоров с одним вузом оформляются как несколько взаимодействий.
- Дополнительные соглашения и лицензии относятся к договору и не считаются отдельными взаимодействиями, пока для них не требуется независимый процесс.

### Ограничение

Если заказчик подтвердит, что одно взаимодействие должно объединять несколько независимо согласуемых договоров, потребуется отдельная сущность взаимодействия над экземплярами workflow: `Interaction 1 -> N WorkflowInstance` и `Interaction 1 -> N Contract`.

## 6. Состояния взаимодействия

### Жизненный цикл

```text
draft -> in_progress <-> blocked -> completed
  └───────────────┴──────────────> cancelled
```

| Состояние | Значение |
| --- | --- |
| `draft` | Взаимодействие создано, но процесс ещё не запущен |
| `in_progress` | Взаимодействие активно, выполняется текущий этап |
| `blocked` | Продолжение временно невозможно; обязательна причина |
| `completed` | Достигнут один из финальных этапов шаблона |
| `cancelled` | Взаимодействие досрочно прекращено; обязательна причина |

### Результат и причина закрытия

Жизненный статус не должен подменять бизнес-результат. Для завершённого или отменённого взаимодействия отдельно фиксируются:

- `outcome`: `successful`, `partial`, `unsuccessful`;
- `closure_reason`: отказ вуза, отказ ИТ Школы, нет контакта, потеря актуальности, дубль, иное;
- текстовый комментарий;
- автор и время закрытия.

Если процесс дошёл до предусмотренного финального этапа «Отказ», взаимодействие получает `completed` с результатом `unsuccessful`. Если пользователь прекращает процесс до финального этапа, используется `cancelled` с обязательной причиной.

## 7. Проверка решений по ТЗ заказчика

### Подтверждено ТЗ

- Предмет контроля — взаимодействие с вузом.
- Workflow — автоматизированный и визуализируемый путь этого взаимодействия.
- Путь начинается до появления договора: поиск контакта, коммуникация, встреча и подготовка документов предшествуют подписанию.
- Данные из сайта и LMS должны добавляться в существующий или новый workflow.
- Взаимодействие охватывает выбранные программы и продукты.
- Следовательно, конкретное взаимодействие обоснованно моделировать как `WorkflowInstance`, но не как шаблон или версию шаблона.

### Не определено ТЗ и является проектным решением

- количество взаимодействий у одного вуза;
- ограничение `Взаимодействие 0 -> 1 Договор`;
- допустимость параллельных взаимодействий;
- статусы и результаты взаимодействия;
- версионирование и жизненный цикл версий шаблона.

### Итог

Принятая модель ТЗ не противоречит. Терминологически следует фиксировать: `WorkflowTemplate` — типовой путь, `WorkflowVersion` — его редакция, `WorkflowInstance` — конкретное взаимодействие с вузом. Ограничение одного договора на взаимодействие остаётся MVP-допущением и требует подтверждения заказчика.

## 8. Названия разделов интерфейса

### Решение

- Основной раздел «Договоры» переименовать во «Взаимодействия».
- Действие «Новый договор» заменить на «Новое взаимодействие».
- Основная карточка — «Взаимодействие с вузом».
- Договор показывать отдельной вкладкой или блоком внутри карточки взаимодействия.
- В карточке вуза показывать список взаимодействий, а не только договоров.
- Поиск должен искать «взаимодействие или вуз»; номер договора остаётся одним из поисковых атрибутов.

### Предлагаемая карточка взаимодействия

```text
Процесс | Программы и продукты | Договор | Контакты | Файлы и комментарии | История
```

Отдельная вкладка «Обзор» не создаётся. Над вкладками постоянно отображаются две согласованные по высоте карточки:

- «Сведения» — вуз, ответственный, дата начала, программы и продукты, источник взаимодействия;
- «Обзор взаимодействия» — статус, текущий этап, SLA этапа, следующее действие и краткое состояние договора.

В карточке «Обзор взаимодействия» процесс представлен только текущим этапом и следующим действием; полная схема и работа с переходами находятся во вкладке «Процесс».

В реестре взаимодействий показываются вуз, статус взаимодействия, текущий этап, ответственный и результат. Номер и статус договора выводятся как необязательные поля: до подписания договора их может не быть.

## 9. Проверка модели базы данных

### Общий вывод

Большинство текущих таблиц оправданы требованиями. Отдельную таблицу `interactions` добавлять не нужно: бизнес-сущностью взаимодействия становится `workflow_instances`. Также не нужен отдельный workflow договора.

### Что изменить

- `workflow_instances`: убрать обязательную зависимость от договора; добавить обязательные `university_id`, `manager_id`, а также источник, результат и сведения о закрытии.
- `contracts`: связать с `workflow_instance_id`; для MVP связь должна быть `0 -> 1`, поэтому нужен уникальный ключ.
- `contract_contacts` переименовать в `interaction_contacts`.
- `contract_programs` переименовать в `interaction_programs`.
- `contract_products` переименовать в `interaction_products`.
- `comments` и `attachments` привязать к `workflow_instance_id`, а связь с конкретным `workflow_event_id` оставить необязательной.
- `licenses` оставить отдельной сущностью и связывать с договором и продуктом взаимодействия.
- Ответственного хранить на взаимодействии; не дублировать его в договоре.
- Вуз договора получать через взаимодействие; не дублировать связь без необходимости.

### Что оставить

- вузы и контакты вузов;
- пользователи и доступ к вузам;
- направления, программы, продукты, вендоры и их справочные связи;
- шаблоны, версии, этапы, переходы, экземпляры и события workflow;
- договоры и лицензии;
- заявки и обучающиеся;
- интеграции, импорты, аудит, настройки и технический счётчик кэша.

### Что не добавлять сейчас

- отдельную таблицу взаимодействий;
- отдельный workflow договора;
- отдельную историю статусов договора: на первом этапе достаточно общего аудита;
- второй набор программ и продуктов одновременно для взаимодействия и договора;
- отдельную таблицу состояний этапов: они вычисляются из событий.

### Дополнительная проверка

- Контакты вузов и вендоров оставить: они нужны для коммуникации по взаимодействию и сопровождения продуктов.
- Связь `program_products` оставить при наличии реальных исходных данных о соответствии программ и продуктов.

## 10. Интеграции с LMS и сайтом

### Что требует ТЗ

- Получать JSON по API из LMS и сайта ИТ Школы.
- Загружать данные в существующий или новый workflow.
- Использовать данные для статистики востребованности программ: заявки, обучающиеся и потоки.
- Точные контракты и утверждённые поля должны быть предоставлены заказчиком.

### Что реализовано сейчас

- Два адаптера: LMS и сайт.
- Работа по сети либо через тестовый JSON/загрузку файла.
- Обновление справочников программ, продуктов, вузов и контактов.
- Загрузка заявок и обучающихся.
- Защита от повторного создания записей через внешние идентификаторы.
- Ручной запуск руководителем или администратором и журнал результатов.
- Новая заявка вуза сейчас создаёт договор-черновик и запускает workflow.

### Целевая логика

```text
Внешний API
-> адаптер
-> проверка и нормализация
-> поиск по внешнему идентификатору
-> обновление статистики и справочников
-> привязка к взаимодействию или создание взаимодействия-черновика
-> журнал результата
```

- Заявка отдельного обучающегося с сайта учитывается в статистике и сама по себе не создаёт взаимодействие с вузом.
- Заявка вуза на сотрудничество создаёт новое взаимодействие в статусе `draft`, если подходящего открытого взаимодействия нет.
- Если открытое взаимодействие по вузу и программе найдено, данные добавляются в него как событие или комментарий.
- Интеграция не создаёт фиктивный договор. Договор появляется только в ходе процесса.
- Автоматический запуск workflow из черновика допускается только после подтверждения ответственного либо при отдельно настроенном доверенном сценарии.
- Повторная синхронизация обновляет существующие записи и не создаёт дубли.

### Согласованное разделение заявок

- Заявка студента на обучение и заявка вуза на сотрудничество — разные типы данных и разные бизнес-сценарии.
- Заявки студентов поступают с сайта и используются только для статистики востребованности программ: количество заявок, обучающихся и потоков.
- Заявка студента не создаёт взаимодействие, workflow или договор.
- Взаимодействие создаётся только по заявке вуза на сотрудничество либо вручную сотрудником ИТ Школы.
- Персональные данные студента сохраняются только в минимально необходимом объёме; если для отчётов достаточно агрегатов, персональные данные хранить не следует.

### Что оставить в БД

- `integration_sources` — источники и их включение;
- `integration_runs` — журнал запусков;
- `external_links` — соответствие внешних и внутренних объектов;
- `learning_applications` — заявки на обучение;
- `learners` — минимальные данные обучающихся.

### Что требуется уточнить после получения контрактов API

- стабильные внешние идентификаторы вузов, программ, заявок и обучающихся;
- поля программы, потока, статуса обучения и дат начала/завершения в LMS;
- режим обмена: расписание, webhook или ручной запуск;
- правила обновления и удаления данных;
- нужен ли отдельный результат `partial` для запуска с частично ошибочными записями;
- нужна ли отдельная связь обучающегося с программой и потоком (`enrollment`).

## 11. Единый справочник статусов

### Правило

- В БД и API хранится стабильный английский код.
- Во фронтенде код отображается через единый словарь локализации.
- Русские названия не используются в бизнес-логике и запросах к API.
- Статусы разных сущностей не подменяют и не дублируют друг друга.

### Шаблон workflow (`WorkflowTemplate`)

| Код | Русское название |
| --- | --- |
| `enabled` | Активен |
| `disabled` | Отключён |

### Версия workflow (`WorkflowVersion`)

| Код | Русское название |
| --- | --- |
| `draft` | Черновик |
| `active` | Действующая |
| `deprecated` | Устаревшая |
| `retired` | Выведена из использования |

### Взаимодействие (`WorkflowInstance`)

| Код | Русское название |
| --- | --- |
| `draft` | Черновик |
| `in_progress` | В работе |
| `blocked` | Заблокировано |
| `completed` | Завершено |
| `cancelled` | Отменено |

Результат взаимодействия хранится отдельно: `successful` — успешно, `partial` — частично успешно, `unsuccessful` — неуспешно.

### Этап взаимодействия (`WorkflowStage` в рамках экземпляра)

| Код | Русское название |
| --- | --- |
| `not_started` | Не начат |
| `active` | Активен |
| `completed` | Завершён |
| `skipped` | Пропущен |
| `blocked` | Заблокирован |

Состояние этапа вычисляется по текущему этапу и событиям workflow, а не хранится отдельной сущностью.

### Договор (`Contract`)

| Код | Русское название |
| --- | --- |
| `draft` | Черновик |
| `active` | Действует |
| `suspended` | Приостановлен |
| `closed` | Закрыт |
| `cancelled` | Отменён до вступления в силу |

Для `closed` отдельно хранится причина: `fulfilled` — исполнен, `expired` — истёк срок, `terminated` — расторгнут.

### Лицензия (`License`)

| Код | Русское название |
| --- | --- |
| `active` | Действует |
| `expired` | Истекла |
| `revoked` | Отозвана |

### Программа во взаимодействии

| Код | Русское название |
| --- | --- |
| `not_started` | Не начата |
| `in_progress` | Внедряется |
| `implemented` | Внедрена |
| `suspended` | Приостановлена |

### Передача продукта

| Код | Русское название |
| --- | --- |
| `not_started` | Не начата |
| `in_progress` | Выполняется |
| `transferred` | Передан |
| `suspended` | Приостановлена |

### Требование к фронтенду

Фронтенд использует один централизованный словарь вида `entity.status_code -> localized_label`. Один и тот же код может иметь разные русские формы для разных сущностей, поэтому общий словарь только по коду без контекста использовать нельзя.

## 12. Ролевая модель

### Основание по ТЗ

- В ТЗ используются формулировки «Пользователь — КАМ», «Руководитель» и «Администратор платформы».
- Для системы принимаются три однозначных названия ролей: «Менеджер», «Руководитель» и «Администратор».

### Единые названия ролей

| Код роли | Русское название |
| --- | --- |
| `manager` | Менеджер |
| `head` | Руководитель |
| `admin` | Администратор |

- Коды ролей в Keycloak, backend, API и frontend всегда пишутся на английском: `manager`, `head`, `admin`.
- В русском интерфейсе и документации используются только названия: «Менеджер», «Руководитель», «Администратор».
- «Пользователь» — общее обозначение любого авторизованного сотрудника, но не отдельная роль.
- «КАМ» — должность из ТЗ, но не название системной роли.
- Формулировка «Администратор платформы» допустима только как пояснение назначения роли `admin`; отображаемое название роли — «Администратор».

### Проект решения — на согласование

Роль, функциональные права и область видимости данных должны быть разделены:

```text
Role -> набор разрешённых действий
DataScope -> доступные взаимодействия и вузы
ExplicitGrant -> дополнительные точечные доступы
```

- Роли не наследуются автоматически. Если сотрудник совмещает функции, ему явно назначаются несколько ролей.
- `manager`: ведёт взаимодействия только в своей области данных, работает с workflow, контактами, программами, продуктами, договором, файлами и отчётами.
- `head`: видит взаимодействия своей управленческой области, назначает ответственных, контролирует сроки и проблемы, формирует сводные отчёты; исключения workflow выполняет с обязательной причиной и аудитом.
- `admin`: управляет пользователями, ролями, областями доступа, справочниками, импортом, шаблонами workflow, интеграциями, аудитом и системными настройками.
- `admin` по умолчанию не получает доступ к содержимому взаимодействий и персональным данным. Временный служебный доступ выдаётся отдельно и журналируется.
- Удаление начатого взаимодействия, договора и вуза не является штатным правом роли: используются отмена, закрытие или архивирование. Физическое удаление допустимо только для ошибочно созданного объекта без зависимостей.

### Области данных

| Код | Русское название | Назначение |
| --- | --- | --- |
| `own` | Свои | Назначенные пользователю взаимодействия и явно доступные вузы |
| `team` | Команда | Взаимодействия менеджеров управленческой области |
| `all` | Все | Все бизнес-данные организации |
| `none` | Нет доступа | Только административные функции без чтения бизнес-данных |

Для MVP `head` может иметь область `all`, если заказчик подтвердит отсутствие отдельных команд. Иначе требуется связь руководителя с командой менеджеров.

### Выявленные пересечения текущей реализации

- В Keycloak руководителю дополнительно назначен `manager`, администратору — `manager` и `head`; роли смешаны с иерархией полномочий.
- Backend и frontend автоматически дают `admin` все права руководителя, включая все взаимодействия и персональные данные.
- `head` может не только назначать ответственных, но также запускать интеграции, менять вуз и представление workflow; эти полномочия прямо не закреплены ТЗ.
- Менеджер видит общий каталог вузов и может создать договор по вузу вне своей области ответственности.
- Любой `head` видит все договоры; управленческие команды в модели отсутствуют.
- `admin` может физически удалять договоры и вузы, что опасно для истории и аудита.
- Раздел интеграций и его журнал видны менеджеру, хотя запуск ограничен руководителем и администратором.

Диаграмма вариантов использования: `use-case.puml` в корне проекта.

## 13. Программы и продукты во взаимодействии

### Решение

- ИТ-программа — основная образовательная сущность взаимодействия.
- ИТ-продукт — инструмент, используемый для реализации одной или нескольких программ.
- Продукт существует самостоятельно в общем справочнике, поскольку имеет собственного вендора, описание и контакты.
- Во взаимодействии продукт не может существовать без связи хотя бы с одной программой.
- Набор программ и продуктов определяется на уровне взаимодействия, а не договора: работа с ними начинается до появления договора.

### Целевая модель

```text
ItDirection 1 -> N ItProgram
Vendor 1 -> N ItProduct
ItProgram N <-> M ItProduct                 — допустимое соответствие в справочнике

WorkflowInstance 1 -> N InteractionProgram
WorkflowInstance 1 -> N InteractionProduct
InteractionProgram N <-> M InteractionProduct — фактическое использование во взаимодействии
```

Связь фактического использования реализуется отдельной таблицей `interaction_program_products` между `interaction_programs` и `interaction_products`.

### Правила

- Сначала во взаимодействие добавляется программа, затем для неё выбираются продукты.
- Выбирать можно только активные программы и продукты.
- По умолчанию интерфейс предлагает продукты, связанные с программой в справочнике `program_products`.
- Продукт вне справочного соответствия можно добавить только как осознанное исключение с комментарием; право на исключение имеет Руководитель.
- Один продукт может использоваться в нескольких программах одного взаимодействия без создания дублей `InteractionProduct`.
- Нельзя удалить программу, пока с ней связаны продукты; сначала связи должны быть перенесены или удалены.
- Если продукт больше не связан ни с одной программой взаимодействия, его следует удалить из состава взаимодействия либо потребовать новую связь.
- Архивные элементы справочника сохраняются в существующих взаимодействиях, но недоступны для нового выбора.

### Статусы

- `InteractionProgram.implementation_status`: `not_started`, `in_progress`, `implemented`, `suspended`.
- `InteractionProduct.transfer_status`: `not_started`, `in_progress`, `transferred`, `suspended`.
- Для программ и продуктов используются разные перечисления и разные словари локализации.
- Статусы относятся к взаимодействию и не должны храниться второй раз в договоре.
- Изменение статуса должно согласовываться с workflow: автоматическое изменение выполняется событием соответствующего этапа, ручное исключение требует комментария и попадает в аудит.

### Требуемые исправления текущей реализации

- `contract_programs` заменить на `interaction_programs`.
- `contract_products` заменить на `interaction_products`.
- Добавить `interaction_program_products` для фактической связи программы и продукта.
- Отделить `ProductTransferStatus` от `ProgramImplementationStatus`; для продукта заменить `implemented` на `transferred`.
- Запретить добавление неактивных справочных записей.
- Не сопоставлять программы и продукты из интеграций только по названию: использовать внешний идентификатор, а при его отсутствии — контролируемое ручное сопоставление.
- Передать ведение бизнес-связей программ и продуктов Руководителю, а не Администратору.

## 14. Шаблоны договоров с типовыми значениями

### Предложение — на согласование

Добавить бизнес-сущность `ContractTemplate`, которая хранит типовые настройки договора и используется при создании договора внутри взаимодействия. Это дополнительное улучшение: прямого требования автоматического формирования договора в ТЗ нет.

### Возможная модель

```text
ContractTemplate 1 -> N ContractTemplateVersion
Contract N -> 1 ContractTemplateVersion
WorkflowInstance 0 -> 1 Contract
```

Шаблон может содержать:

- название и тип договора;
- стандартный срок действия;
- типовые значения и комментарии;
- перечень обязательных полей;
- перечень необходимых документов;
- при необходимости файл типового документа DOCX.

### Предлагаемая логика

- Руководитель создаёт, редактирует и вводит шаблоны в действие; Администратор не управляет их бизнес-содержанием.
- При создании договора Менеджер выбирает действующий шаблон.
- Система копирует типовые значения в новый договор и подставляет известные данные взаимодействия: вуз, ответственного, программы, продукты и выбранные контакты.
- Номер договора, даты, реквизиты и итоговый подписанный файл вводятся или загружаются отдельно.
- Договор хранит ссылку на использованную версию шаблона и собственный снимок значений.
- Изменение шаблона не изменяет созданные ранее договоры.
- Предлагаемые состояния версии шаблона: `draft` — «Черновик», `active` — «Действующая», `archived` — «Архивная».
- Полную генерацию юридического документа следует реализовывать только после получения утверждённых шаблонов, реквизитов сторон, правил нумерации и согласования от заказчика.
